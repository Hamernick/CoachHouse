# Organization forms

Private form-draft contracts and a controlled question builder, embedded in the existing workspace Particle editor. Source: `docs/plans/2026-10-14-workspace-framed-editors-and-forms.md`.

`index.ts` exposes pure Zod contracts and editing helpers. `client.ts` exposes the builder, public intake and private response components. The host owns authorization, draft persistence, conflicts, history and pending state. A Form Activity widget persists only the private definition through the existing graph writer. Responses must never be stored in board JSON.

Drafts permit unfinished questions. Publication has a separate validator for meaningful labels and unique, nonempty choice options. Stable question UUIDs survive reorder/type changes. Editing is local until the host's explicit Add/Save; no added polling, request on keystroke or independent store.

Thirteen manual question types: short answer, paragraph, email, number, single choice, multiple choice, dropdown, date, time, linear scale, rating, multiple choice grid and checkbox grid. Scale/rating share bounded integer answers, immutable published endpoints, optional120-character labels, keyboard-accessible wrapped44px controls and clear selection. Scale starts at0/1 and ends at2–10; rating starts at1 and ends at2–10. Existing writers serve definitions, public answers and staff corrections; no new storage or migration. Grids support up to20 rows and10 columns with stable UUID axes,240-character labels, required-row validation and mobile stacked controls. Publication needs at least one named row and two distinct named columns. Stored immutable-version membership governs single-column or unique column-set answers; historical labels survive draft edits. Grid answer payloads count toward the existing total bound. Shared public/correction controls display row and column labels. Single/checkbox choices now optionally enable Other; strict `{ optionIds, otherText }` uses reserved `other` identity within the version/question and separate trimmed text up to2,000 characters. A selected Other requires text even on an optional question; deselection removes it. Ordinary choices remain strings/arrays, dropdown has no Other, and legacy definitions remain unchanged. Saved-version membership and existing total-answer bounds apply before submit/correction. Shared response cells display/edit the text with ordinary labels. The original six stored types remain compatible. Dropdown preserves version-scoped option IDs; Date stores a validated calendar date (`YYYY-MM-DD`, years 0001–9999) and Time stores `HH:mm`, with no timezone conversion. Native date/time pickers use shared Input styling; dropdown uses shared Select and can be cleared. Add inserts at the top; rows expand to edit, duplicate, reorder or remove. Copies receive fresh UUIDs and independent option arrays, up to 50 questions. Separate 44px handles support mouse/touch/keyboard reorder, Escape/outside cancellation and editing-lock checks; move-up/down controls remain. Existing draft writers persist order and copies; published versions and answers are unchanged. Existing shadcn controls, semantic tokens, keyboard access, reduced-motion-safe opacity/translation and touch targets are reused.

Preview rehearses those questions using component-local answers and explicit validation. Switching back to editing discards rehearsal answers only. Changes to the definition reset the preview. The host Particle form is never submitted by preview text-entry shortcuts, and native email validity cannot block Add/Save. No network or persistent storage is involved.

`form-version.ts` builds strict detached, deeply readonly snapshots and version records. Choice IDs are scoped to the immutable version and question; they are not identities across edits/publications. `form-answers.ts` validates bounded typed answers and exact form/version bindings. The native server validates these contracts against stored versions; publication/audience and response identity are rechecked transactionally. Pure validators alone never authorize or persist.

Native intake uses `server/intake-service.ts`, the `server.ts` facade and `/api/public/forms/intake`. Migrations `20261101140000_organization_form_intake.sql`, `20261101150000_organization_form_creation.sql`, `20261101160000_organization_form_recovery.sql` `20261101170000_organization_form_reviewers.sql` `20261101180000_organization_form_editors.sql` `20261101190000_organization_form_managers.sql` `20261101200000_organization_form_source_access.sql`, `20261101210000_organization_form_source_recovery.sql` and `20261101220000_organization_form_owner_access.sql` must precede this app revision. Public/invited submissions have immutable versions, exact retry and current-audience checks. Private response lists support historical versions, authorized refresh and direct revision-checked corrections. Responses never enter board JSON. API bodies are bounded; initial admission caps are 60/minute and 1,000/day per canonical form.

New intrinsic forms receive canonical `creator_id` and manager attribution on their first saved board write. Session actor identity is verified independently of client `updated_by`; service writes must supply an authorized actor. Existing intake managers remain unchanged; historical creator IDs stay null, and previously unregistered legacy drafts receive organization-owner custody, not invented authorship. The database guard protects source edits/removal across main/named canvases and board replacement; layout is independent. Publication cannot claim ownership. Source deletion retains identity and private responses.

Canonical primary managers grant View/Edit/Manage per form through Responses or the saved form inspector’s Form access disclosure, before or after publication. Access targets exactly one version ID or organization/form pair. Explicitly granted organization owners and membership-backed organization editors with View read responses; Edit additionally permits canonical source edits and direct answer corrections. Manage adds View/Edit delegation, restricted to access that delegate granted. Only the primary manager can grant Manage or change independent grants. Saving a delegated grant directly adopts it as independent access. Publication and source removal/conversion remain primary-manager-only. Removal/downgrade of Manage removes its dependent grants atomically. Owner recipients need no membership row; a generated nullable membership key preserves the non-owner membership foreign key, and all recipients reference an Auth account. Optional owner membership changes do not change explicit grants. Non-owner membership demotion/deletion fences affected forms and removes grants and children; losing the primary manager removes the complete chain. Restoring membership does not restore grants. Recovery invalidates prior manager revisions. Strict `source_access` reads drive the Particle inspector’s fail-closed editing controls with visible five-second refresh; revoked unsaved drafts remain available. Every writer checks current authority under database locks. The access UI uses exact retry and revision checks; delayed retries cannot undo a later downgrade. Non-editor/external Edit/Manage and lifecycle qualification remain unfinished; page/organization roles never imply response access. Native Google Sheets, exports, saved response tables and hosted acceptance remain unfinished. Existing unbound shared forms remain previews.

It transfers management only after explicit confirmation and a current eligibility/revision check; creator, published versions and answers stay intact. `server/recovery-service.ts` uses the service-only recovery RPC, exact operation receipts and answer-free audit metadata. Active managers cannot be displaced. Unknown outcomes retain the original command. No hosted migration has been applied.

Authorized viewers can copy a version-specific response link from Responses. `/forms/responses/[versionId]` lives outside the dashboard; `server/response-entry.ts` validates the UUID and verified session, preserving the login return path. The client reuses the existing authorized response/correction/access RPCs; URLs grant no permission. Private URLs are excluded from telemetry and indexing. Clipboard fallback, mobile containment and revoked-content removal are covered by `form-response-entry.spec.ts`. This provides isolated version entry. Read-only external invitations are implemented below; broader discovery and external source editing remain unfinished.

Primary form managers create read-only invitations inside Responses. Recipients sign in with the verified invited email and explicitly accept on the response link; no email is sent. Pending invitations expire after seven days, while accepted access lasts until revoked/invalidated. Reinviting requires new acceptance. Invitation identities and operation receipts are private; session-only commands use `organization_form_viewer_access`. Form locks serialize acceptance/revocation/response reads; primary manager loss permanently revokes invitations, and recovery invalidates their manager revision. No organization membership, public/page grant, source edit, correction or wider form discovery follows. Existing View/Edit/Manage grants remain separate.
